# verity_team

Verity is from minecraft or from backrooms?

## Профили компаний и групп

Скрипт сохраняет факты источников, связывает компании с физическими лицами, агрегирует платежи и создаёт профили групп. Требуется Python 3.9+ со стандартным модулем SQLite. Сторонние библиотеки, LLM, RAG и сбор новостей не используются.

## Запуск

```bash
python3 build_profiles.py \
  --companies /path/to/df_Uid_data_hack.csv \
  --payments /path/to/df_Uid_payment_hack.csv \
  --persons /path/to/df_Fid_Uid_link_hack.csv \
  --out-dir output \
  --top-n 10

python3 -m unittest discover -s tests -v
```

Запускайте команды из папки со скриптом. `--top-n` принимает неотрицательное целое число; `0` отключает рейтинги. Входные CSV читаются как UTF-8, в том числе с BOM, с разделителем `;`. Исходные файлы не изменяются. Обязательны все столбцы из констант `COMPANY_FIELDS` (24), `PAYMENT_FIELDS` (4), `PERSON_FIELDS` (4); дополнительные поля компаний и связей людей также сохраняются. Ошибки схемы, кодировки и количества полей останавливают запуск с понятным сообщением.

Платежи загружаются построчно во временную SQLite-базу; файл не загружается целиком в память и не перечитывается для каждой компании. База создаётся внутри `--out-dir` и удаляется после завершения. Для неё и результатов нужно свободное место на диске. Готовые файлы заменяют предыдущие только после успешных контрольных сверок.

## Результаты и схема

Все файлы JSON/JSONL имеют UTF-8. JSONL содержит один самостоятельный JSON-объект на строку. Профили сортируются по строковому ID, связи — по плательщику и получателю, исходные наблюдения — по номеру записи. Порядок детерминирован. Денежные значения — десятичные строки без лишних конечных нулей, счётчики — целые JSON-числа; неизвестное значение — `null`.

| Файл | Содержимое |
| --- | --- |
| `company_profiles.jsonl` | Одна запись на уникальный непустой `SYNTHETIC_U` из справочника, включая конфликты. |
| `group_profiles.jsonl` | Одна запись на непустой непротиворечивый `GROUP_ID`, имеющий допустимых участников. |
| `payment_edges.jsonl` | Все направленные пары `PAYER → BENEFICIARY` с известными идентификаторами, включая неизвестных справочнику контрагентов и самоплатежи. |
| `data_issues.jsonl` | Проблемы данных, исключённые записи и конфликты с воспроизводимыми ссылками на источник. |
| `summary.json` | Статистика загрузки, покрытие справочником, результаты контрольных сверок. |

Профиль компании:

- `synthetic_u`, `status`: идентификатор и `ok` либо `conflict`.
- `facts.raw_records[]`: исходные поля в `values` без потери текстового представления и `source`.
- `facts.normalized`: отдельно нормализованные значения с исходными именами полей; для конфликтного ID — `null`.
- `derived.group_id`: принятая группа либо `null`.
- `derived.persons[]`: `synthetic_f` и массив `observations` с исходными и нормализованными значениями, включая `CITY_NAME` и `RC_NAME`, и происхождением.
- `derived.payments`: `incoming`, `outgoing`, `self_payments` и `observation_status`. Для направления сохраняются `amount`, `count`, число исходных, принятых и исключённых строк, число уникальных контрагентов, покрытие и `top_counterparties`. `unpairable_rows` и `unpairable_source` описывают строки с известным ID этой компании, но пустым вторым концом.
- `labels[]`: пересекающиеся метки наблюдаемых признаков с основанием в исходных полях.
- `quality`: полнота, пропуски и обнаруженные противоречия.

У направленной связи есть `payer`, `beneficiary`, `is_self_payment`, `amount`, `count`, `source_rows`, `accepted_rows`, `excluded_rows`, `duplicate_extra_rows`, `payer_status`, `beneficiary_status` и `source.records`. Идентификатор, отсутствующий в справочнике, сохраняется со статусом `unknown`; отдельная карточка в `company_profiles.jsonl` для него не создаётся. В покрытии `known_counterparties` включает `ok` и `conflict`, а `conflict_counterparties` выделяет конфликтные ID внутри известных. Число контрагентов относится ко всем наблюдаемым парам, включая пары только с исключёнными числовыми данными. Рейтинг включает пары с принятыми строками, сортируется по сумме по убыванию, затем по ID по возрастанию.

Профиль группы содержит `group_id`, `members`, `provenance` и `derived`: число участников; отрасли, регистрационные регионы и страны ФТС с массивами соответствующих участников; продуктовые счётчики `true_count`, `false_count`, `unknown_count`; `members_revenue_sum` со значением и покрытием. Сумма выручек участников не является консолидированной выручкой.

Запись `data_issues.jsonl` содержит `code`, `source` и дополнительные поля конкретной проблемы, например `raw`, `problems` или конфликтные `variants`. Связи людей с неизвестными компаниями полностью сохраняются там с кодом `person_unknown_company`. В `summary.json` находятся разделы `sources`, `companies`, `persons`, `payments`, `edges`, `groups`, `payment_flows`, `coverage`, `issues`, `checks`, `policies`; `all_checks_passed` объединяет результаты сверок. Версия схемы — `1.0`.

В `source.file` указано имя исходного файла, в `source.record` — номер записи данных начиная с 1, **без заголовка**. Это логическая CSV-запись, которая может занимать несколько физических строк файла. Для агрегированных платёжных ссылок и предупреждений о местоположении человека до 1 000 записей `source.records` содержит их номера. Для большего числа записей `records` равно `null`, а `record_count` и точный `selector` позволяют воспроизвести выборку: пара идентификаторов после удаления внешних пробелов, точные исходные поля дубля, известный ID с пустым вторым концом или нормализованный `SYNTHETIC_F`. Это ограничение длины ссылки, а не размера данных или числа принимаемых строк. Полные пути, SHA-256, размеры и заголовки источников сохранены в `summary.sources`. Происхождение агрегированных признаков группы восстанавливается через участников и их исходные записи.

## Правила интерпретации

- Идентификаторы и ОКВЭД остаются строками, ведущие нули сохраняются. В нормализованных текстовых полях убираются внешние пробелы. Флаги `0.0`/`1.0` преобразуются в `false`/`true`, пропуск — в `null`.
- `FTS_COUNTRY_NAME` разделяется по запятым; пробелы и повторения удаляются, страны сортируются, исходный пропуск становится `null`. Перечень стран не устанавливает направление торговли. Флаг ФТС и метка `fts_information_flag` означают наличие сведений ФТС. Несогласованность флага и списка стран отражается в отчёте, оба исходных факта сохраняются.
- Возраст и численность сохраняются как категории. Показатели ФНС и СПАРК остаются раздельными.
- `CITY` и `REGION` — регистрация компании. `CITY_NAME` и `RC_NAME` в связях физических лиц сохраняются отдельно. Несколько вариантов местоположения одного `SYNTHETIC_F` дают предупреждение `person_location_variants` и отметку `quality.person_ids_with_location_variants` в профиле компании; без периода наблюдений варианты не разрешаются.
- По приложению 1, `NEGATIVEMARK` — признак ключевого собственника, а не негативный риск. Кредитный флаг не устанавливает сумму долга или ставку. Роли пользователей интернет-банка в CSV отсутствуют.
- `REVENUE_COMPANY` описана как годовая выручка, но год, единица и валюта источником не установлены. Они остаются `null`; денежные пороги не применяются. Для платежей валюта и период также неизвестны.
- Совпадающие нормализованные записи компании допускаются с сохранением всех исходных вариантов. Если варианты различаются, создаётся `conflict`: достоверная объединённая карточка не строится, варианты и различия сохраняются в отчёте. Консервативная политика исключает такой ID целиком из групповых агрегатов, даже если отдельное поле совпадает.
- Группы определяются только по принятому `GROUP_ID`. Пустые значения не образуют общую группу. Общий человек или платёж не доказывают владение, должность или общий холдинг. Признак участника не переносится на остальных.

## Платежи и контроль

Одна строка принимается в расчёт, только когда оба идентификатора непустые, `PAY_AMT` — конечное корректное десятичное число, а `PAY_CNT` — неотрицательное целое число. Если сумма или счётчик ошибочны либо пусты, исключается **вся строка**; причина и исходные значения сохраняются в `data_issues.jsonl`. Пропуски не заменяются нулями. Отрицательные суммы сохраняются с предупреждением: без признака возврата или корректировки оснований автоматически менять их знак нет.

Повторяющиеся направленные пары суммируются точно, без `float`. Совпадающие платёжные строки тоже учитываются: идентификатор операции и период отсутствуют, поэтому технический дубль не доказан. Совпадения и число исходных строк сообщаются отдельно.

`PAYER == BENEFICIARY` учитывается только в `self_payments`, исключается из обычных входящих/исходящих потоков, числа контрагентов и рейтингов. При отсутствии принятых наблюдений сумма и счётчик остаются `null`; истинный наблюдаемый ноль сохраняется как ноль. `observation_status` принимает `no_observations`, `only_excluded` или `observed`. Строка с пустым концом не образует направленную пару, но учитывается как исключённое наблюдение у известного конца и сохраняется в отчёте. Отсутствие строк в файле не доказывает отсутствие деятельности.

Связи физических лиц обрабатываются отдельно и присоединяются после агрегации, поэтому несколько людей у компании не размножают платёжные суммы.

Контрольные сверки проверяют сохранение суммы и количества принятых платежей между исходными строками, направленными связями, обычными потоками и самоплатежами; отчётность исключённых строк; состав групп и сохранение неизвестных контрагентов. Суммы двух направлений не складываются друг с другом: один обычный платёж появляется один раз как исходящий и один раз как входящий.

## Проверенные источники

Изучены PDF «Альфа Хак_Новостная аналитика.pdf», включая приложения 1 и 2 на страницах 15–17, и фактическая структура трёх CSV. В приложении 2 перечислены аналитические материалы банка, готовой классификации профилей там нет. На странице 16 у платёжной таблицы указан ошибочный заголовок файла; тип данных определён по фактическим столбцам `BENEFICIARY;PAYER;PAY_AMT;PAY_CNT`.

Исходные файлы содержат 85 525 строк компаний, 1 380 585 строк платежей и 12 514 связей физических лиц. В справочнике 85 514 уникальных ID. ID `U_428697` имеет 12 противоречащих друг другу вариантов; это результат общей проверки уникальности, специальной обработки этого ID в коде нет.

## Результат запуска на предоставленных файлах

Пройдены 19 содержательных тестов на Python 3.9.6: обычные профили и группы, несколько стран, конфликты ID, неизвестные контрагенты, независимое присоединение людей, самоплатежи, повторяющиеся пары и строки, точность сверх стандартных 28 цифр `Decimal`, ошибки и пропуски, пустые группы, BOM, схема, детерминизм, неполные пары и компактное происхождение больших агрегатов. Журнал — `test_results.txt`.

Созданы 85 514 профилей компаний, 18 091 группа с 85 513 допустимыми участниками и 1 380 568 платёжных пар. Все контрольные сверки в `output/summary.json` пройдены. Дополнительный отчёт независимой сверки источников и готовых файлов — `verification.json`. Платёжные строки с ошибочными числами или пустыми идентификаторами в этих файлах не обнаружены; все 1 380 585 строк приняты.

| Поток по всем концам связей, включая неизвестные компании | Сумма в единицах источника | Количество платежей |
| --- | ---: | ---: |
| Все принятые строки | 55 991 235 586 000 | 24 515 786 |
| Обычные исходящие = обычные входящие | 10 269 508 255 000 | 21 256 928 |
| Самоплатежи, 27 406 строк | 45 721 727 331 000 | 3 258 858 |

Обнаружены 9 повторяющихся направленных пар с 17 дополнительными строками; одна дополнительная строка полностью совпадает с другой и сохранена. В платёжных связях 114 552 ID отсутствуют в справочнике компаний. В файле физических лиц 7 885 связей относятся к 7 788 неизвестным компаниям; эти наблюдения сохранены в отчёте. У 258 физических лиц есть несколько вариантов местоположения, а в 14 строках отсутствуют город и регион.

Есть 430 несогласованностей ФТС: 206 строк со странами при выключенном флаге и 224 строки с включённым флагом без стран. Поле численности СПАРК пусто в 85 357 строках, `ECO_MARK_LABEL` — в 4 157. У 21 907 компаний нет платёжных наблюдений в предоставленном файле. Эти факты описывают покрытие и качество источников, а не риск компаний.

## Состав репозитория

В ветке находятся скрипт, синтетические тесты и документация, а также отчёты выполненной локальной проверки `test_results.txt` и `verification.json`. Исходные CSV и PDF передаются отдельно. Пять файлов результата создаются командой запуска в `output/`; данные и большие выгрузки исключены через `.gitignore`. Хеши в `verification.json` относятся к проверенному локальному запуску на предоставленных источниках.
